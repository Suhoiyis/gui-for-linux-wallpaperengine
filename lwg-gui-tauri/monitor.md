### 🎨 界面元素详解与交互逻辑

#### 1. 顶部概览区 (System Overview)

- **布局**: 三列卡片网格 (`Gtk.Grid`)。
- **视觉重点**:
  - **大数字**: CPU (%) 和 Memory (MB) 使用大号字体。
  - **动态颜色**:
    - 🟢 **绿色**: 负载 < 20% (健康)
    - 🟠 **橙色**: 负载 20% - 40% (警告)
    - 🔴 **红色**: 负载 > 40% (高危)
  - **火花图 (Sparkline)**: 每个卡片底部有一条微型折线图，展示过去 60 秒的趋势。CPU 图是红色的，内存图是蓝色的。

#### 2. 进程详情列表 (Process Details)

- **布局**: 垂直堆叠的卡片 (`Gtk.Box` with vertical orientation)。
- **单行结构**:
  - **左侧**: 图标 (区分 Backend/Frontend/Tray) + 进程名 + PID。
  - **中间**: 命令行名称 (过长会截断显示 `...`) + 实时数值 (CPU/Mem/Status)。
  - **右侧**: 两个并排的微型图表 (CPU 趋势 & 内存趋势)。
- **折叠面板 (Expander)**:
  - 点击 `▼` 展开更多细节。
  - **Thread Details**: 列出该进程下的所有线程。代码会对线程名进行“清洗” (例如将 `linux-w:disk$0` 显示为 `Disk I/O 0`)。
  - **Wallpaper Info** (仅 Backend): 如果这是后端进程，会显示当前正在渲染的壁纸缩略图、标题、作者和 ID。

#### 3. 截图历史面板 (Screenshot History)

- **布局**: 位于页面最底部，独立区域。
- **表头**: 标题 + 右上角的 `[Clear]` 按钮 (用于清空历史记录)。
- **列表项**:
  - **缩略图**: 左侧显示截图的小预览 (或默认相机图标)。
  - **信息**: 壁纸名称 + 截图时间戳。
  - **性能指标**:
    - `⏱️ Duration`: 截图耗时。
    - `📈 Max CPU`: 截图期间的 CPU 峰值。
    - `💾 Max Mem`: 截图期间的内存峰值。
  - **操作按钮**:
    - `[📂] Open Folder`: 调用系统文件管理器打开文件夹。
    - `[🖼️] Open Image`: 直接调用默认图片查看器。

### 💡 动态行为

- **实时更新**: 整个页面没有“刷新”按钮。数据通过 `perf_monitor` 回调每秒多次自动更新，图表会像心电图一样流动。
- **自动增删**: 如果某个进程崩溃或重启，对应的卡片会自动从列表中消失或重新出现，无需用户干预。
- **Y 轴自适应**: 迷你图表的 Y 轴最大值会根据数据动态调整。如果 CPU 只有 1%，图表会自动放大波动，让你能看清微小的变化，而不是变成一条直线。

这个设计既满足了**极客**对底层数据的需求（线程、PID、实时图表），又照顾了**普通用户**的直观体验（颜色预警、截图历史、壁纸预览）。

当我们把视角拉高，放到**“完整的 Rust + React 桌面应用”这个维度时，真正的“优化”才刚刚开始。接下来的优化不再是“改代码结构”，而是“优化数据流”**。

以下是你接下来需要关注的 3 个深层优化方向：

1.  数据流策略优化：从“轮询”到“事件驱动” (Polling vs. Event-Driven)

    现状（Mock 阶段）：
    你的 useSystemStats 里面用的是 setInterval（每秒执行一次）。这叫轮询 (Polling)。
    TypeScript

    // 现在的逻辑
    setInterval(() => {
    setStats(生成随机数据...)
    }, 1000);

    问题：
    当连接到 Rust 后端时，如果你在 Rust 里也写一个“每秒查一次”，然后在前端“每秒问一次 (invoke)”，这会有两个问题：

        延迟：前端请求 -> Rust 处理 -> 返回数据，这中间有来回的开销。

        不同步：如果 Rust 检测到 CPU 瞬间飙升（比如 0.1秒内），但前端的 setInterval 刚好错过了这个时间点，你的图表就会漏掉峰值。

    优化方案（Event-Driven）：
    利用 Tauri 的 Event System (emit / listen)。

        Rust 端：启动一个独立线程，每当系统资源变化（或者固定频率），主动向前端发射事件。

        前端 Hook：
        TypeScript

        import { listen } from '@tauri-apps/api/event';

        useEffect(() => {
          // 被动接收数据，而不是主动去问
          const unlisten = listen('system-stats-update', (event) => {
            setStats(event.payload);
          });
          return () => { unlisten.then(f => f()); };
        }, []);

    收益：响应更快，开销更小，不仅是性能优化，更是架构升级。

2.  内存与计算优化：环形缓冲区 (Ring Buffer)

    现状：
    你的 Mock 数据里是这样写的：
    TypeScript

    const updateArr = (arr, val) => {
    // 数组切片 + 追加
    return [...current.slice(1), { val }];
    };

    每次更新数据，你都创建了一个全新的数组。

    潜在问题：

        虽然 JS 引擎很快，但在高频（比如 60FPS 刷新）下，每秒创建几十个新数组并触发垃圾回收（GC），可能会导致微小的卡顿。

        如果不小心没限制数组长度，cpuHistory 会无限增长，导致内存泄漏。

    优化方案：
    在 Rust 后端实现一个固定大小的环形缓冲区（例如只存最近 60 个点）。前端只负责接收这 60 个点进行渲染，甚至只接收“最新的一个点”，由前端维护一个固定长度的数组，确保内存占用永远是常数级 O(1)。

3.  可视化渲染优化：SVG vs Canvas

    现状：
    你使用的是 recharts。它是基于 SVG 的。
    SVG 的原理是：每个数据点都是一个 DOM 元素（<path>, <circle>）。

    潜在瓶颈：
    如果你的图表变得很复杂（比如同屏显示 4 个核心的波形，每个波形 100 个点），那一瞬间就有 400+ 个 DOM 节点在变化。React 的 Diff 算法和浏览器的重排（Reflow）压力会变大。

    未来优化路径：
    如果未来你发现 Performance 页面导致 CPU 占用过高（这就搞笑了，监控软件自己占用了大量 CPU），你需要考虑将图表库换成基于 HTML5 Canvas 的库（例如 Chart.js 或 uPlot）。Canvas 是位图绘制，不管多少数据点，它只是一张图，性能是 SVG 的几十倍。

    不过，以目前的 30-60 个点来看，Recharts 依然是够用的，这点目前不必急着改。
